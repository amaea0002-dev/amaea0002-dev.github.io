Incident Response Plan

A · When to declare an incident

Pick the severity in the first 5 minutes. Err one level higher — easy to downgrade, costly to upgrade late.

Sev 1
Critical — declare immediately

Confirmed personal data leaving the system to an unauthorised party, confirmed cross-firm data exposure, total outage of app.amaea.co.uk > 15 min, or compromise of any production secret being actively exploited.

Examples: customer reports seeing another firm's data · Anthropic announces a breach affecting us · admin email account compromised · RLS bypass discovered in prod

Sev 2
Significant — declare within 1 hour

Suspected but unconfirmed data exposure, leaked secret with no evidence of exploitation, single feature degradation (RAG returning errors, RMAR generation broken), or cost-explosion attack against an endpoint.

Examples: secret accidentally committed to git · vendor security advisory but exposure unknown · cron job failing repeatedly

Sev 3
Minor — log and address within 24 hours

Contained, low-impact issue. Single user affected, no data exposure, no regulator obligation triggered. Document, then fix in normal cadence.

Examples: single user can't log in · email delivery delayed but not lost · minor UI flaw with security implication

B · First-hour playbook

Run these five steps in order for any Sev 1 or Sev 2 incident. Don't skip ahead — order matters under stress.

1

Detect & verify

Confirm what's actually happening before acting. A customer report saying "I see another firm's data" might be a screenshot from before today's RLS migration. A "leak alert" might be a public Supabase anon key (these are designed to be public). Verify the claim against the actual production state before you trigger anything else.

2

Declare & assign DRI

Pick the severity (above). Pick the DRI (Directly Responsible Individual) — for technical incidents, Milan; for customer/regulator-facing comms, Hasna. State both explicitly in a message to the other co-founder so there's no ambiguity. Use Signal or phone — don't rely on email under pressure.

3

Contain

Stop the bleeding before investigating. Specific containment actions per incident type are in the runbooks below. The default rule: if a credential might be compromised, rotate it; if a route might be exposing data, take it down; if an account might be compromised, sign all sessions out and force a password reset. Containment first, root cause second.

4

Communicate

Internal: keep the other co-founder informed with short factual updates ("Containment done. Investigating scope. Will update in 30 min."). External: do not communicate to customers until you have confirmed facts — speculation in writing becomes evidence later. ICO clock starts when Sev 1 with personal data is confirmed (see ICO decision flow). FCA notification only applies once we have signed pilot customers.

5

Document — even before resolution

Open a timestamped note (Apple Notes or a markdown file in a private gist). Log: detection time, what was observed, who was told, what was done, what was assumed. This is your evidence base for the postmortem AND for any regulator filing. Don't trust your memory — incidents distort time perception. Write it as it happens.

Sev 2 1 · Leaked / exposed API key Expand →

Triggers

A production secret is suspected exposed: accidental commit to a public repo, paste into a chat/issue, screen-share recording, screenshot in a deck, vendor-side leak. Sev 1 if there is active evidence of exploitation; Sev 2 otherwise.

Containment (do these in order — same flow we used on 18 May 2026 for the full 6-key rotation)

  1. Identify the key. Which env var? Which Vercel project (amaea, amaea-brand, amaea.ai)? Some keys live in multiple projects (e.g. Resend).
  2. Open the 1Password Secure Note for that project. This is the master record.
  3. Generate the replacement in the vendor dashboard. Copy the new value to a temp note (Apple Notes with FaceID lock).
  4. Update 1Password with the new value first — never skip this.
  5. Update .env.local in amaea-app/ (or matching directory): open -e /Users/milan/Documents/Amaea/amaea-app/.env.local
  6. Update Vercel — Dashboard → project → Settings → Environment Variables. Keep the Sensitive flag ticked. Update in every project that holds the key.
  7. Redeploy: cd /Users/milan/Documents/Amaea/amaea-app && npx vercel --prod --yes
  8. Test the new key works before revoking the old. Run the matching endpoint: chat for Anthropic, embedding endpoint for Voyage, ingest cron for INGEST_SECRET, signin + cron for Supabase.
  9. Revoke the old key in the vendor dashboard.
  10. Delete the temp note. 1Password is now the only place the new value lives.

Special cases

  • Supabase JWT signing key: use the standby-promote-revoke flow. ES256 (ECC P-256) is the SOC 2-aligned algorithm. Do not revoke previous keys until the new sb_publishable_… / sb_secret_… keys are deployed and tested.
  • Resend: shared between amaea and amaea.ai projects. Update both before revoking.
  • NEXT_PUBLIC_* keys are public by design. NEXT_PUBLIC_SUPABASE_URL being exposed is not an incident. Rotation rules apply to secret-side keys only.

Investigation

  • Check vendor usage logs for unfamiliar IPs / unusual call patterns in the window the key was exposed.
  • Anthropic + Resend + Voyage all expose usage dashboards with timestamps. Pull the last 7 days.
  • If the key was committed to git: check whether the commit was pushed to a remote. If yes, assume exposed. Use BFG or git filter-repo to scrub history if the repo is public.

Customer / regulator notification

No personal data exposed by a leaked API key alone → no ICO notification, no customer notification required. If usage logs show actual data exfiltration via the leaked key, this escalates to Runbook 2 (data exposure).

Sev 1 2 · Cross-firm data exposure / RLS break Expand →

Triggers

Customer reports seeing another firm's data, internal audit discovers an RLS policy gap, a query returns rows from firms other than the authenticated user's. This is the highest-stakes incident type — it directly breaches Consumer Duty and UK GDPR.

72-hour clock starts now. If personal data is involved and there is risk to data subjects' rights/freedoms, ICO must be notified within 72 hours of awareness (UK GDPR Art. 33). Document the awareness timestamp in the first 5 minutes.

Containment

  1. Verify the report. Get exact details: which user, which page, what they saw, what time. A screenshot is gold. Do not assume the customer is wrong; do not assume they are right.
  2. Identify the affected route. If it's a single API route, take it down via Vercel: Dashboard → Project → Deployments → most recent → Promote to production a known-good build, OR roll back to the last known-good deployment.
  3. If the scope is unclear, take down the whole app: Vercel Dashboard → amaea → Settings → General → Pause Deployments. Better short outage than continued exposure.
  4. Run the RLS test suite from amaea-app/scripts/test-rls.mjs (or the canonical 46-test suite) against the live database. A test failure tells you exactly which table/policy broke.
  5. Audit the compliance_events table for any cross-firm reads in the exposure window. SELECT ... WHERE created_at > '2026-05-18 09:00' AND user_firm_id != target_firm_id (or similar). This is your scope assessment.

Investigation

  • What was the root cause? Missing RLS policy, service_role bypass on a server-side route that should have used the user client, hard-coded firm ID, broken JOIN that crossed firm boundaries?
  • How long was the gap open? Check git blame on the affected migration/route to find when it was introduced.
  • Who was exposed and to whom? Identify both data subjects (firms whose data leaked) and recipients (who saw it).

Remediation

  1. Fix the underlying policy / route. Write a regression test before merging.
  2. Add a row to compliance_events documenting the fix.
  3. Redeploy. Re-run the full 46-test RLS suite.
  4. Manually verify with a multi-firm test scenario in a non-prod environment.

Notification — required

  1. ICO: see decision flow. Default position for confirmed cross-firm exposure with personal data = notify. Use the ICO breach notification template.
  2. Affected customers: use the customer breach notification template. Send only after ICO is filed (or in parallel for Sev 1, but never before you have confirmed facts).
  3. FCA: only relevant once we have signed pilot customers. For pre-pilot, ICO is the only required regulator.
Sev 1 3 · Vendor breach announcement (Supabase / Vercel / Anthropic / Cloudflare) Expand →

Triggers

A critical vendor publicly announces a breach, security incident, or unauthorised access. Severity depends on what they hold: Supabase (full data tier) and Cloudflare (TLS + DNS) are Sev 1; Anthropic, Voyage, Resend are Sev 2 unless the announcement specifies actual data exposure affecting us.

Containment

  1. Read the advisory carefully. Identify: dates of exposure, what was accessed, whether our project is in the affected list (Vercel and Supabase notify per-org if so), what action they recommend.
  2. Rotate every secret the vendor could have learned. For Supabase: all `sb_secret_…` and JWT signing key. For Vercel: every env var on the platform (it cached them). For Cloudflare: API tokens, Access service tokens, audit DNS for tampering.
  3. Force re-authentication of every active session on app.amaea.co.uk if the breach affects Supabase Auth. SQL: UPDATE auth.users SET aud = aud; followed by signing key revoke (forces re-issue).
  4. Increase monitoring. Watch the vendor's status page + Twitter/X feed for updates. Subscribe to their security mailing list if not already.

Investigation

  • Determine our exposure window. Was our project provisioned during the affected period?
  • Pull our own logs from the vendor (request history, login history) for the exposure window. Look for unfamiliar activity.
  • If the vendor offers a forensic audit option, request it.

Notification

If the vendor confirms our data was exposed → ICO notification (72-hour clock starts at our awareness, not the vendor's). If exposure is suspected but not confirmed → use the non-breach incident template to inform customers proactively. Hasna leads comms. Refer to the vendor's official advisory in our customer notification — do not paraphrase.

Sev 1 4 · Auth bypass discovered Expand →

Triggers

A route is found to be accessible without authentication, or with a wrong-user authentication (token from firm A grants access to firm B's data). Discovered internally (audit), externally (responsible disclosure), or actively exploited (logs).

Containment

  1. Take the affected route down immediately. Rollback to a known-good deployment is fastest if it's a recent regression; otherwise add a guard returning 503 and redeploy.
  2. If exploitation is suspected: revoke all active sessions (Supabase Auth → users → bulk action → sign out all), force password resets, regenerate the JWT signing key.
  3. Audit access logs for the affected route in the exposure window. Look for unauthenticated 200s, or 200s where the authenticated user's firm_id doesn't match the firm_id in the response.

Investigation

  • How did it slip past review? Was the middleware-redirect missing? Was the API route missing its getUser() check? Was the RLS policy default-allow rather than default-deny?
  • Check for sibling routes with the same pattern — bugs of this class are usually copy-paste.

Remediation + regression test

  1. Fix the auth check.
  2. Add a test that the route returns 401 when called unauthenticated AND 403 (or filtered results) when called with the wrong firm context.
  3. Sweep all sibling routes for the same class of bug. Often there are 5–10.

Notification

If logs show actual unauthorised access to personal data → treat as Runbook 2 (data exposure). If logs show only unauthenticated 200s with no personal data returned → no ICO obligation, but disclose to affected customers proactively if they exist.

Sev 1 5 · Email account compromise (founders / shared mailboxes) Expand →

Triggers

milan@amaea.co.uk, hasna@amaea.co.uk, founders@amaea.co.uk (Google Group), or amaea0002@gmail.com shows signs of unauthorised access: unfamiliar sign-in alert, sent emails you didn't send, forwarding rules you didn't add, missing emails.

Containment

  1. Sign out everywhere. Google Account → Security → Your devices → Sign out all other sessions.
  2. Reset the password from a different device (not the one suspected compromised). Use a long, unique passphrase from 1Password.
  3. Audit MFA settings. Check no backup phone or alternate 2FA method has been added without your knowledge. Remove if found.
  4. Audit Google account permissions. Workspace Admin → Security → check connected apps, third-party access, forwarding rules, vacation responders, filters.
  5. For shared mailboxes (founders@): rotate the Google Workspace admin password and any external integrations that posted there.

Investigation

  • Pull the last 30 days of login history from Google Account → Security → Recent security activity. Note unfamiliar IPs/locations/devices.
  • Check the Sent folder for any messages you didn't send.
  • Check forwarding rules — common attacker move is to set a silent forward to an external address.
  • If the account is the admin account on Vercel / Supabase / Cloudflare / GitHub / 1Password: treat all of those as potentially compromised → trigger the full secret rotation runbook.

Notification

If the account had access to customer-data systems (Supabase admin, GitHub, Vercel) → assume customer data was accessible → see ICO decision flow. If it's a purely external-facing inbox with no admin access, no regulator notification, but Hasna should still warn any customers whose emails were in that inbox of potential phishing risk.

Sev 1 6 · DNS / domain compromise Expand →

Triggers

Unauthorised changes to DNS records, the registrar account, or Cloudflare Access policies. Symptoms: amaea.co.uk resolves to an unexpected IP, MX records changed (email routing hijacked), Cloudflare Access policies modified, registrar account password reset email you didn't request.

Containment

  1. Confirm the change is unauthorised. Check Cloudflare audit log: Dashboard → Account → Audit log. Filter on DNS / Access / Zone settings in the last 7 days.
  2. Revert any unauthorised records from the audit log's "previous value" column. Order: A/AAAA records for app.amaea.co.uk first, MX records second, TXT (SPF/DMARC/DKIM) third.
  3. Rotate Cloudflare credentials: API tokens, account password, MFA reset, all Access service tokens. Revoke all active Cloudflare API tokens from Dashboard → My Profile → API Tokens.
  4. Rotate the registrar account. Where is amaea.co.uk registered? (Likely IONOS or Cloudflare Registrar — verify.) Reset that account's password and audit its login history.
  5. Lock the domain at the registrar (registrar lock / transfer lock). Prevents transfer-out attacks during recovery.

Investigation

  • How did they get in? Email account compromise → registrar password reset is the most common path. Check Runbook 5 in parallel.
  • Check Cloudflare audit log for the full sequence of changes. Note the actor's IP.
  • Verify MX records are correct → if MX was changed, email may have been intercepted. Treat as Runbook 5 + check for any password resets initiated during the MX-changed window (those reset emails went to the attacker).

Notification

If MX was changed (email rerouted), all customer communication during that window may have been intercepted. Notify customers directly via known-good channels (not email — use phone or LinkedIn if available). Trigger ICO decision flow if personal data was in any intercepted email.

Sev 2 7 · Cost-explosion attack (runaway AI usage / rate limit breach) Expand →

Triggers

Anthropic or Voyage usage dashboard spikes above expected baseline. Vercel function invocations spike. Single firm exceeds tier cap by >10x. Public chat endpoint (/api/public/chat) being abused by bots.

Containment

  1. Identify which endpoint is hot. Vercel logs filtered by route, sorted by call count over the last hour.
  2. For /api/public/chat: already rate-limited by IP, but verify the limit is firing (200s should drop, 429s should appear). If not, the IP-based limit may need tightening or Cloudflare Bot Fight Mode enabling.
  3. For /api/chat (authenticated): per-firm monthly cap (migration 028, ai_usage_monthly) should already be enforcing. If a single firm is hitting cap, that's working as designed. If multiple firms are spiking, check whether the cap counter is functioning (it had concurrency issues pre-029).
  4. If a specific actor is responsible: sign their session out, suspend the user via Supabase Auth, contact them out of band.
  5. If the platform is being broadly abused: temporarily disable the affected endpoint (return 503 from the route, redeploy).

Investigation

  • Anthropic dashboard: which API key (we should only have one prod key — if multiple, that's a separate problem). Calls per hour, average tokens, cost.
  • Was the spike from one IP, one firm, one route? Distribution matters for the fix.
  • Did the rate limit fail to fire? If yes, that's a code fix; if no, the limit may just need lowering.

Notification

Internal only unless there's a customer-impacting outcome (e.g. a legitimate firm hit cap and was blocked due to attacker noise). No ICO obligation for cost incidents alone — they don't involve personal data exposure.

E · ICO notification decision flow

Under UK GDPR Art. 33, notify ICO within 72 hours of awareness IF there's a "risk to the rights and freedoms of natural persons". Use this flow to decide.

Q1
Was personal data involved?

Personal data = any data identifying a living individual: names, NI numbers, addresses, emails, financial records, advice notes, client review documents. Anonymous logs / aggregate counts are not personal data. → NO: Stop. No ICO obligation. → YES: continue to Q2.

Q2
Was there actual or suspected unauthorised access, loss, or disclosure?

"Suspected" with credible evidence counts. A theoretical possibility (e.g. a key was rotated as a precaution with no evidence of use) does not. → NO: log internally, no ICO. → YES: continue to Q3.

Q3
Is there a risk to data subjects' rights or freedoms?

Default yes for: financial advice records, NI numbers, identity documents, financial account details. Default no for: business contact info that's already public, opt-in marketing data with no sensitivity. When unsure, lean toward yes — ICO would rather hear about a marginal case than learn about it later. → NO: log internally with rationale; consider proactive customer comms anyway. → YES: continue to Q4.

Q4
Is there a HIGH risk to data subjects?

High risk = significant likelihood of identity fraud, financial loss, reputational damage, or psychological harm to individuals. → NO: notify ICO within 72 hrs (template D.4). Notify customers when investigation complete. → YES: notify ICO within 72 hrs AND notify affected individuals without undue delay (Art. 34).

If unsure, file. The ICO accepts preliminary notifications that can be updated as facts emerge. Filing late is the regulatory failure; filing early and revising is normal practice. Phone the ICO helpline (0303 123 1113) for live guidance if the situation is genuinely ambiguous.

H · Quarterly access & supply-chain audits

Run every quarter (next: 2026-08-18). Triggered by the April 2026 Context.ai / Vercel OAuth compromise — supply-chain attacks now arrive via vendor OAuth integrations, not just compromised packages.

  • Vercel — team members + Integrations. Remove inactive members; audit every OAuth-connected app for active need + minimum scopes.
  • GitHub org — members, OAuth apps, deploy keys. Same questions.
  • Supabase — team + API tokens. Confirm only ES256 signing key is “in use”; legacy JWT keys revoked. Audit non-canonical API keys.
  • Google Workspace — admin.google.com → Security → API permissions + third-party app access. Confirm only known apps reach amaea.co.uk mail/drive.
  • Cloudflare — API tokens + Access service tokens. Revoke any unused.
  • 1Password Family Organizer — confirm only Milan + recovery vault. Audit guest invites / shared items.
  • Anthropic / Voyage / Resend / Sentry — confirm only known team accounts have access; rotate abandoned API keys.

Document the audit in the decisions log. If any anomaly is found, treat as a potential Runbook 3 (vendor compromise) trigger.
