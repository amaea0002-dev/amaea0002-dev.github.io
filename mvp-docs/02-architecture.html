Architecture principles

1. Multi-tenancy via Row Level Security

Every tenant table carries a firm_id column. Supabase RLS policies enforce at the database level that an authenticated user can only read or write rows where firm_id = auth.jwt() ->> 'firm_id'.

This is the single most important architectural decision in the schema. Even if application code has a bug that constructs the wrong query, the database rejects it. There is no path to cross-tenant data leakage short of a deliberate database configuration change.

Helper function get_firm_id() (introduced in migration 003_users.sql) returns the firm_id from the current JWT and is used by all RLS policies. The same function is used by the match_firm_embeddings RPC for RAG retrieval, ensuring firm-specific embeddings never leak across tenants.

2. Append-only audit trail

The compliance_events table is insert-only. RLS policies block both UPDATE and DELETE on this table. It is the source of truth for the Compliance Activity Log report and is intended to satisfy FCA SYSC 9 record-keeping (minimum 7 years).

Every meaningful action in the system writes a row here: document uploads, integration syncs, risk flag resolutions, report generations, AI chat queries (with token counts), and manual cleanup actions.

3. Computed metrics, not stored

Dashboard numbers (compliance health score, missing-document count, overdue review count, vulnerable-client documentation %) are computed at query time via PostgreSQL views, not stored as columns. This guarantees they're never out of sync with underlying data. Caching can be added later if performance requires it; at MVP scale (< 1000 clients per firm), live queries are sub-100ms.

Key views (defined in 012_views.sql):

  • v_document_completeness — % of clients with all required doc types complete
  • v_review_completion — % of all reviews in complete status, plus overdue/in-progress counts
  • v_risk_flag_summary — counts by severity + computed penalty score
  • v_firm_health_scores — weighted composite: 40% doc + 35% review + 25% flag
  • v_dashboard — single row per firm with everything the dashboard needs
  • v_vulnerable_doc_status — vulnerable-client documentation coverage

4. Snapshots for reports

When a report is generated, a snapshot of the underlying data is saved as JSONB in the reports.data column. This means a report generated on 11 May 2026 will always show the same content when retrieved later, even if client records have changed since. This matches how FCA reporting works (RMAR submissions are point-in-time) and means historical reports are auditable.

Reports with status = 'complete' are locked from UPDATE via RLS.

5. Per-document validated metadata

documents.metadata is a JSONB column added in migration 017. It stores the per-document-type extracted fields produced by the AI extraction pipeline. The shape varies by documents.type — a fact_find has attitudeToRiskRating, a db_transfer_report has transferValue and coolingOffNoticeProvided, an aml_cdd has cddLastRefreshedDate, etc.

The application enforces shape consistency via Zod schemas (src/lib/extraction/schemas.ts). The database doesn't constrain the JSONB shape — that's deliberate. The schema can evolve without DB migrations, and per-version shape can coexist as the extraction pipeline matures.

6. Doc-level vs client-level risk flags

risk_flags.source_document_id (added in migration 017) is a nullable FK to documents. When NULL, the flag is client-level (e.g. "this client has an overdue annual review"). When populated, the flag is doc-level (e.g. "this specific DB transfer report is missing a cooling-off notice").

Unique constraints are split:

  • risk_flags_client_level_unique — UNIQUE (client_id, type, is_resolved) WHERE source_document_id IS NULL
  • risk_flags_doc_level_unique — UNIQUE (client_id, type, source_document_id, is_resolved) WHERE source_document_id IS NOT NULL

This means a client can simultaneously have one client-level missing_signature flag AND multiple doc-level missing_signature flags (one per source document).

RPCs (Remote Procedure Calls)

  • match_fca_documents(query_embedding, match_threshold, match_count) — semantic search against fca_documents. Used by chat + report generation. Default threshold 0.60, top-6.
  • match_firm_embeddings(query_embedding, match_threshold, match_count) — semantic search against firm_embeddings for the current firm only (uses get_firm_id()). Default threshold 0.45, top-12.

Helper view (migration 017)

documents_with_flag_count

Convenience view joining documents with a count of open flags raised from each.

CREATE OR REPLACE VIEW public.documents_with_flag_count AS
SELECT
  d.*,
  COALESCE(
    (SELECT COUNT(*) FROM public.risk_flags rf
     WHERE rf.source_document_id = d.id AND rf.is_resolved = false), 0
  ) AS open_flag_count
FROM public.documents d;

Data flow: document upload

1. User drags PDF(s) onto /import page
2. Optional: ticks "Treat these N files as ONE document"
3. processAll() in ImportClient.tsx:
   - If group toggle ON + 2+ files: single POST with all files in one FormData
   - If OFF: sequential POSTs, one per file
4. POST /api/import/documents:
   a. auth check (Supabase server client)
   b. resolve firm_id from users table
   c. parse all files via formData.getAll('file')
   d. base64-encode each file
5. processDocument(files):
   a. classifyDocument(files) → Claude vision call with all files as content blocks → DocumentType
   b. extractDocument(files, type) → Claude vision call → JSON → Zod.parse → ExtractedDocument
6. matchClient(extracted, firmId) → look up client by reference, then by name fuzzy match
7. Upload all files to Supabase Storage (firm-documents bucket)
8. Persist documents row:
   - file_name = "primary.pdf" or "primary.pdf (+N more)"
   - metadata = ExtractedDocument + { additionalFiles: [...], totalFiles: N }
9. flagsFromExtraction(extracted) → array of RiskFlag descriptors
10. Upsert each flag into risk_flags with source_document_id = the new doc id
11. Resolve any pre-existing missing/expired risk flags for this client+type
12. If annual_review: mark overdue review complete, create next scheduled review
13. Insert compliance_events row for audit trail
14. Return JSON: { success, doc_type, doc_date, client_name, client_ref, raised_flags, extraction, ... }
15. Frontend updates the result card with extracted fields + raised flag pills

Data flow: chat query

1. User asks question in dashboard chat OR /assistant OR /insights AskAmaea
2. POST /api/chat with { messages: [...], stats: {...} }
3. Build context (Promise.all in parallel):
   a. retrieveFcaContext(query)
      - embedText(query) via Voyage AI
      - sb.rpc('match_fca_documents', threshold: 0.60, count: 6)
      - Fallback to static FCA_KNOWLEDGE if RAG fails
   b. retrieveFirmContext(query)
      - same embedding
      - sb.rpc('match_firm_embeddings', threshold: 0.45, count: 12)
      - Returns empty if firm embeddings haven't been built
   c. getRecentImportContext(firmId)
      - SQL: top 25 doc-level critical/high/medium flags (NOT NULL source_document_id)
      - SQL: top 30 documents with metadata, sorted by uploaded_at DESC
      - Dedupe by (type × client) so re-uploads don't bloat
      - Returns formatted prompt sections "FLAGS RAISED BY RECENT…" + "RECENT DOCUMENT IMPORTS…"
   d. getAdviserStats(firmId)
      - For each adviser: count clients, count overdue reviews
      - Returns "James Morrison (88 clients, 0 overdue), …"
4. buildSystemPrompt(stats, adviserStats, fcaContext, firmContext, importContext, usingRag):
   - Identity + capabilities
   - Live stats from front-end (active clients, overdue, health score)
   - Live adviser stats from SQL
   - Priority client notes (Margaret/Robert/Priya — described as "may have issues, verify")
   - Response guidelines
   - RETRIEVED FIRM CONTEXT block
   - RECENTLY IMPORTED DOCUMENTS AND DOC-LEVEL FLAGS block
   - RETRIEVED REGULATORY CONTEXT block (FCA corpus)
   - Formatting rules (plain prose, no markdown)
5. anthropic.messages.create({ model: 'claude-sonnet-4-6', max_tokens: 16384, system, messages })
6. Log compliance_event with token counts, latency, retrieval query
7. Return { text, ragUsed }

Vercel cron jobs

Defined in amaea-app/vercel.json:

{
  "crons": [
    { "path": "/api/rag/horizon",   "schedule": "0 8 * * 1" },
    { "path": "/api/cron/ar-sweep", "schedule": "0 6 * * *" }
  ]
}

Nightly AR sweep (06:00 UTC daily) at /api/cron/ar-sweep:

  • Queries all overdue reviews across the firm
  • For each: fetches delay-reason notes recorded by the adviser
  • Calls Claude (max_tokens 512) with the review details + notes for a COBS 9.5 sufficiency evaluation
  • If notes are absent or insufficient: creates/updates an overdue_review risk flag
  • If notes are sufficient: resolves any existing overdue_review flag for that client
  • Severity ladder: 8+ weeks = critical, 4–7 = high, 2–3 = medium, <2 = low

Weekly Regulatory Horizon ingest (08:00 UTC Mondays) at /api/rag/horizon:

  • Fetches the FCA RSS feed
  • Parses new publications
  • Embeds each title + abstract via Voyage AI

Architectural decisions worth knowing

Why pgvector and not a separate vector DB. Co-locating embeddings with relational data means we can JOIN client records with their embedded summaries in one query, and we don't operate two systems. Pinecone / Weaviate / Qdrant would add ops burden for no functional gain at MVP scale.

Why Voyage AI and not OpenAI embeddings. Voyage's voyage-3-lite is 512-dim (vs 1536 for OpenAI ada-002 and 3072 for text-embedding-3-large), which means 6× smaller index footprint and faster retrieval at comparable quality on regulatory text. Cost is also ~5x lower. Quality benchmarks were run against the 50-scenario eval set during selection.

Why a discriminated union for ExtractedDocument. Each of the 19 document types has different fields. A discriminated union (z.discriminatedUnion('documentType', [...])) gives us full TypeScript type narrowing — if docType === 'db_transfer_report', we get transferValue: number | null available; if it's a fact_find, we get attitudeToRiskRating: string | null. No type assertions needed.

Why classify-then-extract in two steps, not one. A single prompt asking Claude to both classify AND extract would either be too verbose (every field for every type listed) or too sloppy (Claude inventing fields). Splitting into a cheap classify call (max_tokens 20, just the type identifier) followed by a type-specific extract call gives better accuracy on both steps and lets the prompts stay focused.

Why Zod's .partial() on inner array objects. Claude vision sometimes omits fields it can't determine from a document (e.g. a phone-call touchpoint in an ongoing-service-evidence log doesn't have a chargeLevied field shown). Without .partial(), undefined fields cause schema validation errors. With .partial(), missing fields are tolerated and the validated output represents what was actually extracted.

Why unconditional injection of recent uploads in the chat prompt. RAG retrieval is similarity-based. On broad queries like "give me a compliance rundown", the highest-ranked chunks tend to be firm-overview summaries — specific document_extraction chunks score lower and miss the top-K. Injecting the 30 most recent uploads directly into the system prompt guarantees they're always visible to the model, independent of retrieval. This is the layer that makes the chat able to reference "Margaret's £412,500 DB transfer" by extracted value, not just by general description.

Why we accept doc records without file storage on the document import path. If the Supabase Storage upload fails (bucket misconfigured, file too large), the import route catches the error and proceeds without file_path. The extraction still runs and the metadata is still persisted. We optimise for "compliance state is captured" over "file is archived" because the former is the immediate user value.

What's deliberately not built

These have been considered and parked:

  • Document classification via tool-use rather than free-text response. Anthropic's tool-use API would constrain Claude's output to one of the 19 type values. Free-text + Zod validation is functionally equivalent and easier to evolve.
  • Multi-tenant FCA knowledge base. All firms share fca_documents. Future: per-firm customisation (e.g. a firm's own templates / policies) would live in a separate table.
  • Per-document file versioning. documents.superseded_by FK exists but no UI / pipeline yet creates supersession chains. Reuploading a document of the same type currently UPDATEs the latest record rather than creating a new version.
  • Per-adviser document table (training_competency). Adviser-level documents (SPS, CPD records) currently fail to persist because documents.client_id is NOT NULL. They're extracted and returned to the UI but not stored. A separate adviser_documents table is on the post-MVP list.
  • PDF page-level metadata. For multi-page grouped uploads, we don't record which extracted field came from which page. Adding metadata.fields_by_page is a future enhancement for audit defensibility.
