The AI moat for Amaea is the combination of (a) a substantial proprietary FCA regulatory knowledge base and (b) the dual-RAG retrieval pattern that grounds every chat response and report in both firm data and regulatory text.

This document covers: the FCA knowledge base (sources, ingestion, structure), the embedding model and retrieval RPCs, the chat assistant architecture (dual RAG + unconditional injection), firm embeddings, AI-generated reports, the nightly compliance crons, and the 50-scenario evaluation framework.

Ingestion pipeline

Three Node scripts in amaea-app/scripts/:

fca-scrape.mjs — FCA Publications scraper

  • Uses fetch + pdf-parse v2 (PDF text extraction)
  • Paginates through each category's search results on the FCA website
  • Fetches PDFs or HTML pages
  • Chunks text to ~1,800 characters
  • Supports --resume (skip completed types) and --type (single type) flags
  • Saves to scripts/scraped/*.json

fca-scrape-handbook.mjs — FCA Handbook scraper

  • Uses Playwright (headless Chromium) — required because the Handbook is JS-rendered
  • Navigates chapter index pages, discovers section links, scrapes each section
  • Falls back to scraping the chapter index page directly for single-page chapters
  • Supports --module, --resume, --patch (re-scrape only blank chapters) flags

ingest-scraped.mjs — Bulk ingest to pgvector

  • Loads all scripts/scraped/*.json files
  • Deduplicates by source + title
  • Deletes existing pgvector rows for those sources (clean re-import)
  • Embeds in batches of 8 via Voyage AI (voyage-3-lite, 512-dim)
  • Inserts into fca_documents
  • Supports --dry-run mode
  • Never touches the baseline 82 chunks (different source names)

Run commands

# Publications (skip already-done types)
node scripts/fca-scrape.mjs --resume

# Handbook (patch only blank chapters)
node scripts/fca-scrape-handbook.mjs --patch

# Ingest everything to pgvector
node scripts/ingest-scraped.mjs

# Preview without inserting
node scripts/ingest-scraped.mjs --dry-run

Storage in Supabase

fca_documents table (no RLS — shared corpus):

CREATE TABLE public.fca_documents (
  id           uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
  source       text        NOT NULL,
  title        text        NOT NULL,
  chunk_index  int         NOT NULL DEFAULT 0,
  content      text        NOT NULL,
  embedding    vector(512),
  token_count  int,
  created_at   timestamptz DEFAULT NOW(),
  updated_at   timestamptz DEFAULT NOW()
);

CREATE INDEX fca_documents_embedding_idx
  ON public.fca_documents
  USING ivfflat (embedding vector_cosine_ops) WITH (lists = 50);

IVFFlat with lists = 50 is appropriate for the current ~11k-row scale. If the corpus grows past 50k, retune to lists = sqrt(rows).

Regulatory Horizon (weekly cron)

/api/rag/horizon runs every Monday at 08:00 UTC via Vercel Cron. It:

  1. Fetches the FCA RSS feed
  2. Parses new publications since the last run
  3. Embeds each title + abstract via Voyage AI
  4. Inserts into fca_documents with source = 'FCA Horizon'
  5. Duplicates skipped by URL match

Embeddings

Voyage AI voyage-3-lite

Property Value
Output dimensions 512
Context length 8000 tokens
Cost ~$0.02 per 1M tokens (input)
Latency ~100ms per call

Chosen over OpenAI's text-embedding-3-small/large for compactness (512 vs 1536 dims = 3× smaller index footprint), latency, and quality benchmarks on regulatory text (~5% better mAP on the 50-scenario eval set).

Client at amaea-app/src/lib/rag/embed.ts:

export async function embedText(text: string): Promise<number[]> {
  const cleaned = stripBom(text)  // remove Windows UTF-8 BOM if present
  const res = await fetch('https://api.voyageai.com/v1/embeddings', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json', 'Authorization': 'Bearer ' + VOYAGE_API_KEY },
    body: JSON.stringify({ input: [cleaned], model: 'voyage-3-lite' }),
  })
  return (await res.json()).data[0].embedding
}

Dual RAG retrieval

Every chat query and every AI-generated report section retrieves from two sources in parallel:

1. FCA corpus retrieval

async function retrieveFcaContext(query: string): Promise<string> {
  const embedding = await embedText(query)
  const { data: chunks } = await supabase.rpc('match_fca_documents', {
    query_embedding: embedding,
    match_threshold: 0.60,
    match_count:     6,
  })
  return chunks.map(c => `[${c.source} — ${c.title}]\n${c.content}`).join('\n\n---\n\n')
}

Top-6 chunks at threshold 0.60. Returns formatted FCA citations injected into the system prompt as RETRIEVED REGULATORY CONTEXT.

2. Firm embeddings retrieval

async function retrieveFirmContext(query: string): Promise<string> {
  const embedding = await embedText(query)
  const { data: chunks } = await supabase.rpc('match_firm_embeddings', {
    query_embedding: embedding,
    match_threshold: 0.45,
    match_count:     12,
  })
  return chunks.map(c => `[Firm data — ${c.source_type}]\n${c.content}`).join('\n\n---\n\n')
}

Top-12 chunks at threshold 0.45 (more permissive to admit more firm-specific context). The RPC uses get_firm_id() from the JWT to scope by firm — there's no path to cross-tenant retrieval.

Both retrievals run in parallel via Promise.all. Result: every Claude completion sees both firm-specific signal (which clients are flagged, which docs have been uploaded, what flags are open) and FCA-corpus regulatory grounding (the actual rule text, with chapter/section precision).

Firm embeddings

The firm-specific RAG layer. Rebuilt entirely on every "Refresh AI Context" click (a dashboard button that POSTs to /api/rag/firm-embed).

What gets embedded

buildFirmChunks(firmId) in amaea-app/src/lib/rag/embed-firm.ts produces four types of chunks:

1. client_summary — one per active client with risk signals

For each active client, joins their reviews, vulnerability records, and documents. If the client has any signal (overdue review, vulnerability flag, missing/expired doc), emit a chunk:

Client CLI-0047 Margaret Thompson [adviser: James Morrison]:
  Annual review 423 days overdue (due 2025-03-01).
  Vulnerable client (driver: financial_resilience) — Low savings noted.
  Missing/expired document: letter_of_authority.

2. document_extraction — one per uploaded document with metadata

For each document with non-null metadata (up to 100 most recent), emit a chunk summarising the extracted fields:

Document for CLI-0047 Margaret Thompson — db_transfer_report
(uploaded 2026-05-14, file: 02-db-transfer-gap-margaret-thompson.pdf):
transfer recommended: yes; transfer value: £412,500; cooling-off notice provided:
no; PTS qualification confirmed: yes; client sign-off date: 2026-02-06;
ceding scheme: British Steel Pension Scheme

3. risk_flag — one per unresolved flag

For each unresolved flag (up to 50 most recent), emit a chunk:

Risk flag [CRITICAL] for CLI-0047 Margaret Thompson — No cooling-off notice
provided for DB transfer (COBS 19.1): No cooling-off notice provided for DB
transfer — raised by document upload extraction

4. firm_overview — exactly one per firm

Aggregate counts:

Firm overview:
  Active clients: 261
  Overdue annual reviews: 1
  Vulnerable clients: 4
  Missing/expired documents: 12
  Imported documents with AI extraction: 1765
  Active risk flags — critical: 1, high: 8, medium: 4

Embedding + storage

export async function embedFirmContext(firmId: string): Promise<number> {
  const chunks = await buildFirmChunks(firmId)
  const texts = chunks.map(c => c.content)
  const embeddings = await embedBatch(texts)

  // Clear existing firm embeddings and replace (full rebuild)
  await supabase.from('firm_embeddings').delete().eq('firm_id', firmId)

  const rows = chunks.map((c, i) => ({
    firm_id:     firmId,
    source_type: c.source_type,
    source_id:   c.source_id,
    content:     clean(c.content),
    embedding:   embeddings[i],
  }))

  await supabase.from('firm_embeddings').insert(rows)
  return rows.length
}

Total firm chunks: typically 30-80 for a ~250-client firm.

The chat assistant

Endpoints

  • /api/chat — authenticated chat. Used by dashboard + /assistant + /insights AskAmaea.
  • /api/public/chat — unauthenticated chat for the marketing site demo. Max_tokens 512, no firm data, no recent imports. Prevents abuse via simple rate limiting.

Model

claude-sonnet-4-6 with max_tokens: 16384 (vs the 2048 default — bumped to handle comprehensive compliance walkthroughs without truncation).

Cost per call

At Sonnet 4.6 pricing (~$3/M input, ~$15/M output) with typical real-world usage:

  • System prompt ~ 4-8k input tokens (FCA chunks + firm chunks + recent imports + adviser stats)
  • User question + history ~ 200-1000 input tokens
  • Response ~ 1-4k output tokens (sometimes up to 16k for full rundowns)

Typical per-call cost: $0.05 – $0.20

A firm with active daily compliance usage might generate 20-100 chat calls per day, putting the AI cost at £20-£100 per firm per month. The chat is the most expensive surface in the product — far more than the document import pipeline (which runs ~$0.04 per document).

Unconditional injection (the "always visible" layer)

The system prompt has TWO firm-data layers:

  1. Firm RAG retrieval (top 12 chunks at threshold 0.45) — similarity-based, picks the chunks most semantically related to the user query
  2. Unconditional injection — queries the database directly per chat request for the 25 most recent critical/high/medium doc-level flags + 30 most recent imported documents, dedupes by (type × client), and includes them verbatim

The unconditional layer exists because: on broad queries like "give me a compliance rundown", the highest-ranked RAG chunks are firm-overview summaries, not specific document_extraction chunks. The specific upload data scores lower in similarity and misses the top-K. Without unconditional injection, the chat would frequently fail to reference recent uploads.

This is the layer that makes the chat able to say "Margaret Thompson's DB transfer dated 6 February 2026 was valued at £412,500 with no cooling-off notice" by extracted value, not just by general description.

Live adviser stats

Per request, the chat queries Postgres for each adviser's current overdue review count and active client count, and includes it in the prompt as a line like:

Advisers and current overdue review counts:
James Morrison (88 clients, 0 overdue),
Alex Williams (87 clients, 1 overdue),
Kate Davies (86 clients, 0 overdue)

This replaces a previous hardcoded line in the system prompt that was stale after the seed migrations. The dynamic version means the chat never reasons from stale numbers.

AI-generated reports (Scribe)

/api/reports/generate produces an AI-written executive analysis section for each report type. The endpoint:

  1. Receives { reportType, periodStart, periodEnd } from the client
  2. Loads firm data per the report type (e.g., for RMAR: complaints data, client counts, premium calcs; for Consumer Duty: outcome assessment status across clients)
  3. Calls retrieveFcaContext(reportType-specific query) for FCA-corpus retrieval
  4. Calls Claude (max_tokens 8192) with:
    • System prompt: identity + FCA grounding + clear "no markdown, plain prose" formatting rules
    • User message: the structured firm data + the prompt to write the analysis section 5. Stores the AI output as part of reports.data JSONB 6. Renders as a section in the PDF (or markdown for board summaries)

Snapshot locking

When a report is marked status = 'complete', RLS blocks UPDATE — the report becomes immutable. The full firm-data snapshot lives in reports.data JSONB, so the report can be regenerated from history without re-querying current data.

Nightly AR sweep cron

The most consequential AI-driven background job. Runs daily at 06:00 UTC via Vercel Cron.

What it does

  1. Queries all overdue reviews across every firm: status = 'overdue' OR (status = 'scheduled' AND completed_at IS NULL AND due_date < today)
  2. For each review: fetches the delay-reason notes recorded by the adviser on the client detail page
  3. Calls Claude (max_tokens: 512) with: ``` You are an FCA compliance assistant evaluating an overdue annual review. Under COBS 9.5, firms providing ongoing service must conduct suitability reviews at least every 12 months. The review below is overdue. Read the delay-reason notes (if any) and decide whether they constitute a sufficient justification for the delay.

Review: {clientRef} {clientName}, due {dueDate}, {daysOverdue} days overdue. Delay reason notes: {notes ?? '(none recorded)'}

Respond JSON: { sufficient: boolean, reasoning: string } ```

  1. If sufficient = false OR notes are empty: create or update an overdue_review risk flag
  2. If sufficient = true: resolve any existing overdue_review flag for that client (the adviser has properly explained the delay)

Severity thresholds

Weeks overdue Severity
8+ critical
4–7 high
2–3 medium
Under 2 low

Why it's important

This is the part of the product that turns the platform from "passive monitoring" to "active compliance attention". Every morning, the firm wakes up to a refreshed view of which overdue reviews have been adequately explained and which haven't. The compliance officer can focus on the ones the AI judged insufficient.

Dimension Points What it measures

The .xlsx produces a 2-sheet workbook: Sheet 1 has every scenario with cream-highlighted scoring columns, Total cells with conditional colour formatting (green/amber/red), and a run summary block. Sheet 2 is a full scoring guide with the rubric, what-to-look-for examples per dimension, and total-score interpretation bands. Designed for Hasna to review row-by-row in Google Sheets.

Eval cycle process

  1. Run harness, convert to CSV/XLSX
  2. Hasna scores against ground truth notes in Google Sheets
  3. Identify weak categories (lowest average scores)
  4. Add new FCA chunks to ingest pipeline for those areas
  5. Re-run ingest: node scripts/ingest-scraped.mjs
  6. Re-run eval, compare to baseline
  7. Repeat — each cycle is a measurable RAG improvement

Baseline performance

  • Initial 82-chunk knowledge base (March 2026): scored by Hasna, mean ~6.5/10
  • 11,645-chunk full corpus (May 2026): re-run on same 50 scenarios — pending Hasna scoring as of session end

The expected improvement is on rule citation accuracy (more chapter-precision available) and on enforcement precedent integration (the Final Notices weren't in the baseline corpus).

What's deliberately not built

  • Per-firm custom AI training. Mentioned on the marketing site for the Enterprise tier ("Custom AI trained on your policies"). Not in MVP; would require either fine-tuning or per-firm vector spaces. Phase 4 work.
  • Streaming chat responses. Current chat returns the full completion in one response. Streaming would feel snappier but adds complexity. Worth adding pre-launch.
  • Conversation memory across sessions. Each chat starts fresh — no persistence of past conversations. Adding this is a small backend change but raises GDPR considerations.
  • Tool-use API for structured output. Currently relying on free-text JSON + Zod validation. Anthropic tool-use would constrain output more strictly. Worth testing as a v2.
  • Multi-model orchestration. Could use Claude Haiku for the classify step (cheaper, faster) and Sonnet for extraction. Trade-off is two model dependencies.
  • Per-doc-type fine-tuned models. A future moat. The 50-scenario eval framework is the foundation for this — once we have a scored corpus across thousands of real documents, fine-tuning becomes feasible.
