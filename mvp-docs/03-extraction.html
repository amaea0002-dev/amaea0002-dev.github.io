This is the core IP. Amaea reads IFA compliance documents using Claude vision, extracts compliance-critical fields into validated structured data, and raises specific compliance flags with FCA rule citations when fields are missing or incorrect.

This document covers: the 19 canonical document types, their per-type schemas, the classify-then-extract pipeline, multi-page document grouping, the auto-flag-raising system, and the complete FCA rule mapping table.

The 19 document types

Each type has its own Zod schema (amaea-app/src/lib/extraction/schemas.ts) that defines the extracted fields and the flag-raising rules. The classifier (extract.ts) routes each upload to the right schema.

Client-level documents (extend BaseClientDocFields)

Most documents share a base set of fields (document date, adviser name, client name + reference, signed-by-client booleans, copy-filed/copy-sent booleans, extraction confidence). These are spread into each schema via ...BaseClientDocFields.

  1. suitability_report — SOA / ROA / Suitability Letter Extracted: recommendationSummary, reviewTrigger (new_business / annual_review / ad_hoc), productOrInvestmentReferenced + base fields.
  2. fact_find — Fact Find / KYC / Client Profile Extracted: completionDate, lastUpdatedDate, income/expenditure/assets/liabilities booleans, attitudeToRiskRating (string), capacityForLossRecorded, investmentObjectivesRecorded, vulnerabilityIndicatorsNoted + base fields.
  3. client_agreement — Service Proposition Letter / Terms of Engagement Extracted: dateIssuedToClient, serviceLevelAgreed (ongoing / transactional / one_off / other), ongoingFeeAgreed (string like "0.75% p.a."), subsequentAmendmentDates[] + base fields.
  4. annual_review — Annual Review Report Extracted: reviewMeetingDate, suitabilityReassessed, newRecommendationsMade, nextReviewDueDate, consumerDutyOutcomeIncluded + base fields.
  5. db_transfer_report — Pension Transfer Report Extracted: tvaDate, pensionTransferSpecialistName, ptsQualificationConfirmed, transferRecommended, clientSignOffDate, coolingOffNoticeProvided, schemeName, transferValue (number), cedingSchemeDetails, receivingArrangementDetails + base fields.

Documents with their own field set

  1. vulnerability_assessment — Consumer Duty Vulnerability Record Fields: assessmentDate, adviserName, clientName, clientReference, vulnerabilityDriver (health / life_event / financial_resilience / low_capability), functionalImpact, serviceAdaptations, clientConsentForSensitiveData (boolean — UK GDPR Art. 9), nextReviewDate, extraction confidence.
  2. consumer_duty_outcome — Consumer Duty Client-Level Outcome Assessment Fields: assessmentDate, adviser/client identifiers, outcomeAreasAssessed (array of: products_and_services / price_and_value / consumer_understanding / consumer_support), fairValueConfirmed, concernsIdentified, actionsTakenOrPlanned, nextAssessmentDate.
  3. letter_of_authority — LOA / Third Party Authority Fields: documentDate, dateSignedByClient, providerName, productOrPlanReferenced, authorityExpiryDate, copyFiled, client identifiers.
  4. product_illustration — Key Features Illustration / KFI Fields: documentDate, productProviderName, productType, illustrationReferenceNumber, matchesSoaRecommendationDate, projectedValues (raw text), chargesSummary, client identifiers.
  5. terms_of_business — ToB / Client Consent Form Fields: documentDate, dateIssued, dateSignedByClient, consentsGranted (array of: data_processing / marketing / third_party_referral / special_category_data / other), gdprConsentLanguagePresent, client identifiers.
  6. complaint_record — Complaint Log Entry / Final Response Fields: complaintReceivedDate, natureOfComplaint, adviserNamed, acknowledgedDate, finalResponseDate, outcome (upheld / not_upheld / partially_upheld / withdrawn), redressAmount (number), fosReferralRightsCommunicated, rootCauseCategory, client identifiers.
  7. ongoing_service_evidence — Service Touchpoint Log Fields: client identifiers, adviserName, touchpoints — an array of partial objects: { date, serviceType (meeting/call/report/email/review/other), matchesClientAgreement, chargeLevied, notes }. Inner objects are .partial() to allow the AI to omit fields that aren't applicable to a given touchpoint.
  8. aml_cdd — AML / KYC Verification Record Fields: cddDocumentType (passport / driving_licence / utility_bill / bank_statement / birth_certificate / other), documentDate, verifiedDate, verificationMethod (in_person / electronic / certified_copy), cddLastRefreshedDate, enhancedDueDiligenceApplied, eddReason, client identifiers.
  9. training_competency — Adviser-Level Training & Competency Fields: adviserName, qualificationHeld, awardingBody, spsRenewalDate, cpdHoursTotal, cpdHoursStructured, cpdHoursUnstructured, lastCompetencyAssessmentDate, supervisionStatus (supervised / unsupervised / training). Note: this type has no client_id — adviser-level. Currently extracted but not persisted (DB requires client_id NOT NULL); a separate adviser_documents table is post-MVP.

Doc types added 15 May 2026

  1. expression_of_wish — Pension Death Benefit Nomination Extends BaseClientDocFields. Fields: pensionScheme, pensionPolicyReference, nominees (array of { name, relationship, sharePercent }, .partial()), totalSharePercent (number — should equal 100), witnessSignaturePresent, lastReviewedDate.
  2. application_form — Transfer In / New Account / Wrapper Change Extends BaseClientDocFields. Fields: applicationType (transfer_in / new_account / wrapper_change / withdrawal_instruction / other), receivingProvider (e.g. "Fundment"), receivingProductWrapper (e.g. "Fundment SIPP"), cedingProvider, cedingPolicyReference, transferAmount (number), isDbTransfer (boolean), adviserSignedOff.
  3. portfolio_snapshot — Point-in-Time Valuation Extends BaseClientDocFields. Fields: snapshotDate, totalPortfolioValue (number), numberOfHoldings, riskProfileAtSnapshot, yearToDateReturnPct (number), benchmarkComparison (text). No automatic flags — informational.
  4. sales_file_cover — Compliance File Index / Cover Sheet Extends BaseClientDocFields. Fields: recommendationDate, factFindPresent, suitabilityReportPresent, applicationFormsPresent, illustrationsPresent, termsOfBusinessPresent, complianceOfficerReviewed, complianceOfficerName, complianceReviewDate.
  5. attitude_to_risk — Standalone ATR Questionnaire Extends BaseClientDocFields. Fields: questionnaireProvider (e.g. "FinaMetrica Pro"), questionsAnswered (number), totalQuestions (number), riskRating (string — e.g. "Conservative (3/10)"), riskProfileCategory (conservative / moderately_conservative / balanced / moderately_aggressive / aggressive), reviewedWithClient (boolean), capacityForLossDiscussed.

The extraction pipeline

Step 1: Classify

Single Claude vision call. Output is one of the 19 type identifiers, or unknown.

Function: classifyDocument(files: FileInput[]) in extract.ts.

Prompt (single-file):
  "You are a UK FCA compliance document classifier. Look at this document
   and identify which of the IFA compliance document types listed below
   it is. [TYPE_DESCRIPTIONS table]. Respond with ONLY the type identifier
   (e.g. 'fact_find'). If the document does not match any type, respond
   with: unknown"

Prompt (multi-file):
  "The user has uploaded MULTIPLE FILES that together form ONE document
   (e.g. a multi-part Suitability Report or a multi-page Fact Find).
   Identify which SINGLE document type the combined set represents…"

Each TYPE_DESCRIPTIONS entry includes synonyms found in real-world IFA documents: "SOA", "Statement of Advice", "ROA", "Reasons of Advice", "Suitability Letter" all classify as suitability_report.

Cost: ~$0.01 per call (20 max output tokens, classify prompt + image input).

Step 2: Extract

Single Claude vision call per classified type. Output is a JSON object matching the per-type schema.

Function: extractDocument(files: FileInput[], type: DocumentType) in extract.ts.

Prompt:
  "You are extracting structured compliance data from a UK IFA {type} document.

   Document type: {type}
   Context: {TYPE_DESCRIPTIONS[type]}
   [If multi-page]: The document spans N files which are pages/parts of ONE
   consolidated document. Consider information across all files when
   extracting.

   Extract the following fields and return them as a single JSON object with
   this shape:
   {
     'documentType': '{type}',
     [field listing built from Zod schema with type hints]
   }

   RULES:
   - Return ONLY a valid JSON object. No markdown, no explanation, no fences.
   - Dates in ISO format: YYYY-MM-DD. If a year is missing, return null.
   - For boolean fields: true if clearly shown, false if clearly not, null
     if not determinable.
   - For enums, return the exact identifier from the listed options or null.
   - For 'extractionConfidence', return a number 0–1.
   - Do not invent data. If a field is not present, return null."

The field listing is auto-generated from the Zod schema — type hints like string, boolean, number or null, array of one of: "meeting" | "call" | ….

Step 3: Validate

Output is parsed as JSON, the documentType is forced to match the classifier output (Claude sometimes drops it), enum values are coerced case-insensitively (turn "Upheld" → "upheld", "Life event" → "life_event", including nested array items via recursion), then validated against the Zod discriminated union.

If validation fails: the raw error is logged and returned to the caller. The Zod failures are usually:

  • Missing required fields (undefined ≠ null) — fix by .partial() on nested objects
  • Wrong enum case — handled by coerceEnumsInPlace()
  • Bad date format — Claude needs the prompt to remind it about ISO

Step 4: Flag raising

flagsFromExtraction(doc: ExtractedDocument): RiskFlag[] runs per-type checks and returns an array of { type, severity, rule, reason } descriptors. The route then upserts these as rows in risk_flags with source_document_id linking to the just-created document.

Multi-page document grouping: when the user toggles "Treat these N files as ONE document" on the import page, the frontend sends all files in a single POST with multiple file fields. The route calls processDocument(files) with the array. The classifier and extractor receive all files as separate vision content blocks in one Claude call with a multi-page-aware prompt. The result is one document record with metadata.totalFiles = N and metadata.additionalFiles = [...] recording the secondary file paths.

Flag severity penalty (impacts health score)

The compliance health score uses a weighted penalty on unresolved flags:

  • Critical = −15 per flag
  • High = −8 per flag
  • Medium = −3 per flag
  • Low = −1 per flag

flag_score = max(0, 100 − penalty). Health score = 40% doc completeness + 35% review completion + 25% flag score.

Multi-page document grouping

Real IFA documents are often split across multiple files — a 46-page Suitability Report photographed as 5 separate PDFs, an 18-page ATR questionnaire across 3 files, a 10-page Fact Find as individual pages.

How grouping works

  1. User drops multiple files onto /import
  2. UI shows a checkbox: "Treat these N files as ONE document"
  3. When ticked, the Process button changes to "Process as 1 document (5 files)"
  4. Single POST to /api/import/documents with all files in a single FormData under the same file field name (formData.getAll('file') returns the array)
  5. Route calls processDocument(files: FileInput[]) with all files
  6. Classifier receives all files as separate Anthropic content blocks in a single Claude message, with the multi-page-aware prompt
  7. Extractor consolidates across pages — fields are extracted considering information across all files
  8. Result is one Zod-validated ExtractedDocument
  9. Storage: all files uploaded to Supabase Storage under unique paths
  10. Database: one documents row with:
    • file_name: "primary.pdf (+N more)"
    • file_path: path of the primary file
    • metadata.additionalFiles: array of { name, path } for the others
    • metadata.totalFiles: N

Limits

  • Up to ~20 files per group (Anthropic vision recommendation)
  • Up to ~100 pages of content per Claude call (rough working limit)
  • Total request size limit: ~100MB per Anthropic call

What this enables

What the AI is good at vs not

Based on production behaviour across the 43-PDF test corpus and the real Lucent example documents:

Reliably handles

  • Standard typed/printed documents in PDF form
  • Multi-page documents (with grouping)
  • Mixed prose + tables + checkboxes
  • Specific date extraction (ISO format compliance is high)
  • Specific monetary value extraction (£412,500 etc.)
  • Enum classification (vulnerability driver, complaint outcome, etc.)
  • Signature detection ("Signed by client: [name]" → signedByClient: true)
  • Phone-photographed documents at reasonable resolution
  • Slightly skewed scans (within ~10°)
  • Mixed-quality scans (older docs with degraded contrast)

Sometimes struggles with

  • Hand-completed fields where the handwriting is unclear (returns null rather than guessing — defensive, good)
  • Cases where signature vs initials are ambiguous
  • Multi-column form layouts with dense small text
  • Documents where the same field appears in multiple places with different values (Claude picks one — sometimes the wrong one)
  • Very low-resolution images (< 800px shortest side)

Architectural mitigations

  • Schema validation catches malformed output before it persists
  • Zod's .partial() on nested arrays allows graceful degradation
  • Enum coercion handles case/whitespace variations
  • extractionConfidence field surfaces uncertainty as a flag for human review
  • Compliance flags are advisory, not blocking — a flagged document can still be filed; the flag invites human review

Future enhancements

Tracked in the open items / future-improvements list:

  • Cross-document validation — e.g., does the SOA's recommendation date match the Product Illustration's date? Does the Application Form's transfer amount match the DB Transfer Report's stated value?
  • Auto-grouping by filename pattern — currently users must tick the toggle. A heuristic that detects "SR pt1.pdf" through "SR pt5.pdf" as a group would be a UX win.
  • Consent Form as a separate type — currently lives under terms_of_business. Real CFs are often issued separately; making it a 20th type would let the AI capture the GDPR consent scope more precisely.
  • Per-page field provenance — for multi-page docs, record which extracted field came from which file. Audit-defensibility win.
  • delayReason field on all client docs — previous (v1) pipeline used to extract delay reasons across any doc type to update review notes. v2 dropped this. Worth restoring.
  • Adviser-level document table — training_competency extracts cleanly but doesn't persist because documents.client_id NOT NULL. A separate adviser_documents table would unblock SPS / CPD tracking.
  • Tool-use API for extraction — Anthropic's tool-use would constrain Claude's output to the exact schema shape. Free-text + Zod is functionally equivalent and easier to evolve, but tool-use could improve extraction accuracy on weird edge cases.
