Deployment

Standard deploy

The Vercel CLI deploys the current local state directly — there's no GitHub remote / Git-based deploy at present. From a Mac with vercel login already done:

cd /Users/milan/Documents/Amaea/amaea-app
npx vercel --prod

Vercel:

  1. Uploads the working tree (~90MB compressed)
  2. Runs npm install (picks up dependencies from package.json)
  3. Runs next build
  4. Deploys to the production alias amaea.vercel.app

Typical end-to-end time: 1–3 minutes (faster on warm cache).

First-time deploy on a new machine

# 1. Authenticate Vercel
npx vercel login
# Pick the same method used previously (likely GitHub OAuth)
# Browser opens for confirmation

# 2. Verify the project link
cat /Users/milan/Documents/Amaea/amaea-app/.vercel/project.json
# Should show:
# { "projectId": "prj_51REnXWtZezLKKNAx744qlIqzacN",
#   "orgId":     "team_p5flIlgZvFKNUiGtcywMWfB1",
#   "projectName": "amaea" }

# 3. Deploy
cd /Users/milan/Documents/Amaea/amaea-app && npx vercel --prod

If .vercel/project.json is missing, run npx vercel link first and select the existing amaea project under the amaea0002-devs-projects team.

Rolling back

npx vercel list                          # see recent deployments
npx vercel promote <deployment-url>      # promote a previous deploy to production

Alternatively from the Vercel dashboard: Project → Deployments → click an old one → Promote.

Watching the build

The CLI outputs a JSON summary with deployment ID, inspector URL, and the alias URL. Inspector URL is the Vercel build log.

Environment variables

All set in Vercel Project Settings → Environment Variables with the same values in amaea-app/.env.local for local development. Six required:

Name Where it's used What it does
NEXT_PUBLIC_SUPABASE_URL Browser + server Supabase project URL (used by both auth client and admin client)
NEXT_PUBLIC_SUPABASE_ANON_KEY Browser Anon key for browser-side Supabase calls (RLS-respecting)
SUPABASE_SERVICE_ROLE_KEY Server only Service-role key for admin client (bypasses RLS — used for compliance event logging, cross-firm queries, the AR sweep cron, and the firm-embed rebuild)
ANTHROPIC_API_KEY Server only Claude API for chat, document extraction, report generation, AR sweep
VOYAGE_API_KEY Server only Voyage AI embeddings for FCA ingest, chat retrieval, firm embedding rebuild
INGEST_SECRET Server only Bearer token for manual cron triggers (currently amaea-ingest-2026)

Security notes:

  • SUPABASE_SERVICE_ROLE_KEY is server-only and never reaches the browser. If accidentally leaked: rotate via Supabase Dashboard → Project Settings → API → Reset.
  • ANTHROPIC_API_KEY and VOYAGE_API_KEY — rotate annually or sooner if a deploy log is shared publicly.
  • INGEST_SECRET is only useful for manually triggering crons; rotating it requires updating both Vercel env and any manual trigger scripts.

Migrations

Where they live

  • /Users/milan/Documents/Amaea/amaea-db/migrations/ — the canonical numbered SQL files (001_extensions.sql through 021_atr_doc_type.sql)
  • /Users/milan/Documents/Amaea/amaea-db/supabase/migrations/ — timestamped copies for Supabase CLI compatibility (20260511000001_*.sql through 20260514000021_*.sql)

When adding a new migration: create both copies. The numbered version is human-readable, the timestamped version is what supabase db push would use if we set that up.

Applying a migration

The historic pattern is paste into the Supabase Dashboard SQL editor — not CLI push. To apply migration N:

# 1. Copy to clipboard
pbcopy < /Users/milan/Documents/Amaea/amaea-db/migrations/0NN_name.sql

# 2. Open the SQL editor
open "https://supabase.com/dashboard/project/sqsqyhcrkwjopwlosqlh/sql/new"

# 3. Cmd+V, then click Run

After running, verify with a quick query (often a SELECT against information_schema.columns or a test row INSERT/DELETE).

Migration verification scripts

Available at amaea-app/scripts/:

  • verify-migration-017.mjs — confirms migration 017 schema changes (metadata columns, source_document_id, type CHECKs, view)

  • check-client-signals.mjs — diagnostic for the client query in embed-firm.ts

To run any: cd amaea-app && node scripts/<name>.mjs

Cron inventory

Defined in amaea-app/vercel.json:

{
  "crons": [
    { "path": "/api/rag/horizon",   "schedule": "0 8 * * 1" },
    { "path": "/api/cron/ar-sweep", "schedule": "0 6 * * *" }
  ]
}

/api/rag/horizon — Mondays at 08:00 UTC

Fetches FCA RSS feed, embeds new publications, inserts into fca_documents with source = 'FCA Horizon'. Skips duplicates by URL.

Manual trigger:

curl -X GET https://amaea.vercel.app/api/rag/horizon \
  -H "Authorization: Bearer amaea-ingest-2026"

/api/cron/ar-sweep — Every day at 06:00 UTC

Evaluates every overdue review against COBS 9.5 using Claude. Creates / resolves overdue_review flags. Max_tokens 512 per review.

Manual trigger:

curl -X GET https://amaea.vercel.app/api/cron/ar-sweep \
  -H "Authorization: Bearer amaea-ingest-2026"

Checking cron status

Vercel Dashboard → Project amaea → Logs → filter by /api/cron/. Each cron execution logs with a request ID, duration, and any error.

Routine maintenance

Daily (automated)

  • /api/cron/ar-sweep runs at 06:00 UTC, no human action needed

Weekly (automated)

  • /api/rag/horizon runs Monday 08:00 UTC, no human action needed
  • Check Vercel logs for any cron failures (5-min weekly scan)

Monthly

  • Review Anthropic + Voyage + Supabase usage dashboards for unexpected spikes
  • Run check-health.mjs to confirm demo firm health score is in the expected range
  • Review unresolved risk flag counts — if a flag type is exploding (e.g. 50+ open incomplete_kyc), it may indicate an extraction prompt issue

Quarterly

  • Rotate ANTHROPIC_API_KEY and VOYAGE_API_KEY if not already
  • Re-run the 50-scenario eval against the current FCA knowledge base; record scores
  • Re-validate the demo firm seed data (Sterling IFA still presents well in walkthrough)

Common issues + fixes

Migration breaks because of an existing constraint

Migrations use DROP CONSTRAINT IF EXISTS then ADD CONSTRAINT, which is idempotent. If it fails:

  1. Check the SQL editor error
  2. Common cause: a row that doesn't satisfy the new constraint (e.g., trying to extend a type CHECK while a row has an unknown type). Fix: either UPDATE the offending rows or relax the CHECK temporarily.

A chat request returns empty / errors

# Check Vercel logs first
# Then check the Anthropic dashboard for rate limit or API key issues
# Then check Supabase logs for any RLS denial

If a specific user can't chat: their users row may be missing a firm_id. The chat route falls back to the first firm if user has no firm_id, but RLS-driven queries (like match_firm_embeddings) return empty. Fix: set the user's firm_id directly via the SQL editor.

Extraction fails with Zod validation error

The error message includes the validation path. Common causes:

  • Field expected but Claude returned undefined instead of null → fix: add .optional() or .partial() to the schema
  • Enum value with wrong case → should be auto-handled by coerceEnumsInPlace(), but if it's a nested array enum, verify the recursion is working
  • Date format wrong → Claude returned "15/03/2026" instead of "2026-03-15" → strengthen the prompt or add a date coercion

Quick test: deploy the schema fix, ask user to re-upload. If extraction still fails, the prompt may need refinement.

Firm embeddings show 0 client_summary chunks after a refresh

Common cause: the column-name bug from embed-firm.ts. The Supabase select tries to read a column that doesn't exist (e.g. severity when the actual column is is_vulnerable). Run node scripts/check-client-signals.mjs — if it errors with column does not exist, fix the select clause in embed-firm.ts and redeploy.

Chat doesn't reference recent uploads

Two likely causes:

  1. Firm embeddings stale — Hasna hasn't clicked "Refresh AI Context" since the uploads. The unconditional injection (top 30 docs) should pick them up regardless, but firm RAG retrieval won't.
  2. Cap too low for upload volume — if 31+ documents have been uploaded recently, the oldest get pushed out of the top 30. Either increase the limit (in getRecentImportContext() in chat route) or click Refresh to add them to firm embeddings.

Document upload classified as the wrong type

Inspect the response in the import page result card. The classifier returns one of 19 types. If consistently wrong on a category of document:

  1. Check TYPE_DESCRIPTIONS in extract.ts for the type — does it cover the synonyms Claude is seeing?
  2. Add more synonyms (e.g. "TVAS" for db_transfer_report)
  3. Deploy

Document persisted to wrong client (mis-matched)

The matchClient() function in the import route uses (a) reference number exact match first, then (b) fuzzy name match. If a doc has both, it'll use the reference. If the doc has a similar name to another client, fuzzy match may pick the wrong one.

Cleanup script pattern: find-bad-group-upload.mjs shows how to identify and delete an unwanted doc record + its raised flags. Use this as a template for any cleanup task.

Chat says "no data" but the data is in the DB

Usually a deploy lag issue — the cap bump or schema change hasn't propagated yet. Re-deploy: npx vercel --prod from amaea-app/ and wait 1 minute.

If still failing after deploy: check the actual response payload via the Network tab in browser DevTools. The chat sends back { text, ragUsed }. Check that ragUsed: true. If false, the Voyage API key may be missing or invalid.

Disaster recovery

Database backup

Supabase Pro tier includes automatic daily backups with 7-day retention. To trigger a manual backup:

Supabase Dashboard → Project → Database → Backups → "Create new backup"

To restore: select a backup and click "Restore". Note: this is a full project restore, not selective.

Document storage backup

firm-documents bucket is on Supabase Storage. For a snapshot: use the Supabase CLI:

supabase storage download firm-documents --recursive --output ~/backups/firm-documents-$(date +%F)

Knowledge base rebuild

If fca_documents is corrupted or wiped: the scraped JSON files in amaea-app/scripts/scraped/ are the canonical source. Re-ingest:

cd amaea-app
node scripts/ingest-scraped.mjs

Cost: ~£1 in Voyage AI embedding costs to re-embed 11k chunks.

Firm embeddings rebuild

Per-firm, on demand. The dashboard "Refresh AI Context" button POSTs to /api/rag/firm-embed which calls embedFirmContext(firmId). Rebuilds all chunks for that firm. ~10 seconds per firm at MVP scale.
